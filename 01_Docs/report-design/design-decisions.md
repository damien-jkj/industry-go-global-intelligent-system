## DR-01 补充信息后重新核查报告

**状态：拟议，待组内评审。** 记录日期为 2026-11-23。任务四负责需求—模块对应和报告设计，任务一维护系统需求与版本范围。交互报告是否纳入本期交付，需与需求、数据及后端负责人对齐。[任务四 Issue #2](https://github.com/damien-jkj/industry-go-global-intelligent-system/issues/2) · [任务一 Issue #5](https://github.com/damien-jkj/industry-go-global-intelligent-system/issues/5)

### 要解决的问题

企业出海人员在业务条件不全时，需要先看到现有依据支持的市场与准入信息，再知道哪些条件值得补充。补充或纠正后，用户应能判断哪些结论发生变化、依据是什么、还有什么无法确认。

| 待核验原因 | 适合的处理 |
| --- | --- |
| 缺用户掌握的业务事实 | 在相关条目提供补充入口，说明答案会影响什么，允许选择「暂不清楚」。相同问题关联多条结论时只问一次。 |
| 缺官方资料 | 说明缺少的文件或条款，给出可用的核查入口。用户已经提供的字段可继续使用。 |
| 新旧资料的关系或适用范围不清 | 展示来源和日期。预计进口日期缺失时可补问；文件替代关系和条款适用性需核查官方依据。 |

### 交互取舍

首版拟采用报告条目旁的「补充信息」入口和集中待核验清单，用选择和短文本收集必要事实。侧栏、页内展开等布局由前端评审确定。自由对话和文件上传留待基础流程验证后评估。

1. 用户先查看初筛报告。待核验条目显示原因、所需条件和可采取的动作。
2. 用户补充或更正后，系统预览将重新核查的条目，允许回改答案。提交前提示答案将如何使用。
3. 同一业务场景中，系统根据修改后的条件重查受影响条目，并生成新版本。变更摘要区分用户事实变化和采用新证据，旧版本可回看。若更新失败，旧版本仍可读，答案可用于重试。
4. 补充业务事实可能缩小核查范围。仍缺税目依据、原产资格证明或适用条款时，结论继续显示待核验。

这一设计借鉴 GOV.UK 的必要提问与提交前复核、Microsoft HAX 的纠错及说明操作后果，以及欧盟 ROSA 把问题关联到规则和凭证的做法。[GOV.UK 问题设计](https://design-system.service.gov.uk/patterns/question-pages/) · [GOV.UK 核对答案](https://design-system.service.gov.uk/patterns/check-answers/) · [Microsoft HAX 指南](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/) · [欧盟 ROSA 教程](https://trade.ec.europa.eu/access-to-markets/en/content/how-use-rules-origin-self-assessment-tool-rosa)

### 首轮评审如何验证

用[泰国纯电乘用车样例](report-example.md)演练一轮。初筛版按六位 HS 870380 展示已取得的市场信息，并标记细分税目待核验。用户确认「新车、乘用、整车」后，新版应解释哪些候选因此需要排除或重新核查。若官方依据仍不足，保留税率待核验，并沿用同一口径的市场数据。这是拟议验收场景，具体候选过滤规则由数据负责人确认。

评审先确认四条需求与模块的对应关系：

| 拟议需求 | 对应功能 | 评审要确认的验收点 |
| --- | --- | --- |
| 部分信息缺失时仍能查看初筛 | 初筛报告 | 已有证据的区块可读，缺条件的结论有提示。 |
| 明白什么可以补、为什么要补 | 待核验清单与定向问题 | 能区分业务输入缺失、官方资料缺失与来源冲突，并给出对应动作。 |
| 更正输入后按实际影响重新核查 | 答案复核与新版生成 | 修改车辆信息后重新核查相关条目。证据不足时新版仍说明缺什么。 |
| 理解新旧结果为何不同 | 版本历史与变更摘要 | 能回看旧版，能核对变化条目的输入与来源。 |

需确认首版场景、可用官方资料、至少一个能改变核查结果的补充字段，以及问题与结论的依赖关系。确认后把可交付部分写入需求—模块对应表与报告规格，再定页面和接口。
